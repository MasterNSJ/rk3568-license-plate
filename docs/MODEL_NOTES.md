# 模型与处理流程说明

## 2. 输入、输出与数据约定

### 检测模型

- 原始 ONNX 输入：NCHW，`[1, 3, 640, 640]`，RGB，浮点像素除以 255。
- 输入准备：按比例缩放整图，缩放后宽高取整数截断，居中补边到 640 × 640，补边像素为 114，再将 OpenCV 的 BGR 转为 RGB。
- 当前 RKNN 输入：应用提交 NHWC 的 RGB `uint8` 图像，归一化由转换配置中的 `mean=0`、`std=255` 处理。不要在提交前重复除以 255。
- 转换脚本只导出原始检测头 `792`、`912`、`1032`，形状分别为 `[1,45,80,80]`、`[1,45,40,40]`、`[1,45,20,20]`。
- 每个 anchor 有 15 个字段：框 4、目标分数 1、四角坐标 8、单排/双排布局分数 2。框、角点、筛选及 NMS 由 `plate_persistent/plate_algorithms.h` 解码，不可直接套用普通 COCO YOLO 的字段定义或 anchors。
- 原始 ONNX 的完整输出为 `[1,25200,15]`。三头 RKNN 的输出需要经过应用后处理，才能得到最终的车牌位置。

### LPRNet 识别模型

- 原始 ONNX 输入：NCHW，`[1,3,24,94]`，即宽 94、高 24，颜色顺序为 **BGR**。
- RKNN 输入：应用提交 NHWC 的 BGR `uint8` 图像；转换配置内执行 `(x - 127.5) / 127.5`。不要将检测模型的 RGB 或 `/255` 约定直接用于识别模型。
- 输出语义：68 个类别、18 个时间步。原始 ONNX 为 `[1,68,18]`；当前 RKNN 会出现 `[1,68,18,1]` 的表示。程序按实际输出属性检查并处理支持的排列。
- 输出经逐时间步 argmax、合并连续重复类别、去除 blank 的贪心 CTC 解码得到号码。blank 索引为 67。
- 字符表顺序必须与模型训练时一致。本项目的字母表中 `I`、`O` 位于常用字母序列之后，不可自行重新按字母表排序。
- 当前号码的 7/8 字符、首省份及字母数字位置检查，只是基本格式检查，不代表与真实号码一致，也不是经过校准的识别置信度。

当前两个转换脚本均使用 `do_quantization=False`，没有进行 INT8 数据集校准。这个参数也不意味着设备内全部算子必然以 FP32 执行。

## 3. LPRNet 的 Pow → Mul 兼容处理

在本项目使用的 RKNN Toolkit2 1.3 / 板端运行库 1.3.0 / NPU 驱动 0.8.2 组合中，原始识别图曾在推理阶段发生挂起或堆损坏。连板 Python 调用出现过 `ERROR_PIPE`，板端独立程序出现过 `double free or corruption`。这些现象应结合本地推理和运行库排查，不能一概归因于 USB 连接。

`lprnet/fix_lprnet_pow.py` 只替换经验证的四个 `Pow(x, 2)` 节点：

```text
Pow(x, constant_2)  →  Mul(x, x)
```

替换前检查节点数量、输入输出和常量指数；保留其他节点、权重、模型输入输出与元数据，并保存到独立的兼容 ONNX。原始 `lprnet.onnx` 不覆盖。`convert_lprnet.py` 再由兼容图构建 RKNN，并在成功导出后替换目标 RKNN 文件。

平方与自乘在数学上等价，但改变了旧运行库所走的算子实现。历史 CPU 对照中，原始与兼容 ONNX 的测试输出一致，板端兼容模型恢复运行。由于运行库内部实现不可见，本项目没有定位到闭源运行库中第一次非法写入的具体指令，也不将该现象推广为所有 Pow、所有精度或所有 RKNN 版本均有问题。

## 4. 车牌小图的预处理调整

识别前使用检测得到的四个角点进行透视校正。单排车牌默认围绕中心扩展，四周约留 5% 边距。之后按区域尺寸选择采样方法：

- 留边后的估算宽度至少 188 且高度至少 48：先按四角估算的车牌尺寸透视校正，再通过 `INTER_AREA` 缩小为 94 × 24。
- 较小区域：直接线性透视到 94 × 24。

这样处理是为了控制大车牌缩小过程中的采样损失。它改变的是送入模型的像素，不是识别权重。历史测试中，同一张大车牌照片的首汉字错误随这项调整修正；这不证明所有中文错误都来自预处理，也不保证模糊、反光或遮挡图片都能改善。程序保留原始预测，不用人工替字或截字符掩盖错误。

双排车牌分支包含上下排裁切、拼接再缩放，输出会标注 `double_row_merge_unvalidated`。**该分支尚未得到充分验证，不应据此宣称完整支持双排车牌。** 新能源、特殊牌照、复杂视角等场景也需要按实际使用范围补充验证。

## 5. 常驻后端优化及其边界

`plate_persistent` 的流模式让一个进程在启动时建立两个 RKNN 上下文，随后复用模型处理请求。Qt 通过 `run_stream.sh` 启动它，并通过带请求 ID 的标准输入/输出协议交互。摄像头任务采用有界处理：忙时跳过新的采样请求，避免无限排队和过期结果覆盖当前界面。

这项优化减少重复启动进程、加载模型和建立上下文的开销；不会训练新权重，也不等于每一次 NPU 算子本身都更快。首次请求包含初始化开销，后续请求的表现应单独测量。直接反复执行 `run_image.sh` 仍会每次启动独立的单图进程；Qt 的常驻路径才会复用模型。

性能测量应区分：

1. 预览帧到达速度。
2. 检测/识别接口调用时间。
3. 包含读图、预处理、模型执行、保存结果及进程管理的端到端任务时间。
4. 从虚拟机通过 USB 连板调用的时间。

这些指标不能互换。历史公开图片或单机测试结论也不能直接当作现场准确率、纯 NPU 延迟或摄像头识别帧率。

## 6. 使用与验证基线

项目实际验证环境包括 RK3568、Linux 4.19.232、Qt 5.15.2、匹配目标 sysroot 的 OpenCV 4.5.5、RKNN Toolkit2 1.3 与板端运行库 1.3.0 / 驱动 0.8.2。更换运行库、工具链、模型或预处理后，需要重新核对输入约定及实测结果。

本仓库包含源码、模型和转换脚本，并在 `dist/` 提供从项目最终部署版本整理的 ARM 运行包，内含匹配的 `librknnrt.so` 与随附许可。完整 SDK、工具链和 Qt/OpenCV 系统库没有打包。构建与部署按根 README 执行。当前包不附历史测试图片、测试日志或准确率数据集；部署验收应使用有清晰真实号码的实际图片，并分别检查位置、字符和整体号码。

定位分数来自检测模型，不表示整串号码的正确概率。号码是否正确，仍须与真实车牌核对。
